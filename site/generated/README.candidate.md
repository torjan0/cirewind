# CIRewind

**Reconstruct which GitHub Action commit actually ran—even after a mutable tag
was restored.**

CIRewind is an experimental, evidence-first command-line tool that rebuilds
historical GitHub Actions execution from retained runner, API, and definition
evidence at `run_id + run_attempt + job_id` precision. It keeps preparation
separate from execution and makes missing evidence visible.

## Two-minute local run

```sh
brew install torjan0/tap/cirewind
cirewind demo --out cirewind-demo
cirewind verify cirewind-demo
```

With the supported Go toolchain, `go install github.com/torjan0/cirewind/cmd/cirewind@v0.2.0`
provides the same evaluation build before the demo and verify commands. The demo
needs no credential, network access, or repository clone; it is a synthetic
case, not a real incident.

> **Experimental v0.2.0:** CIRewind has a controlled GitHub.com
> explicit-repository qualification and a deterministic offline demonstration.
> It is not production-ready or complete for every organization, runner layout,
> credential type, or retained-evidence condition. Always inspect collection
> coverage and evidence gaps; do not use CIRewind as the sole basis for declaring
> an incident absent.

## Why CIRewind exists

Current-state dependency inventories cannot reliably answer what a runner used
before a mutable tag moved back to a safe commit. CIRewind preserves and joins
runtime, API, and historical-definition evidence at
`run_id + run_attempt + job_id` precision. It keeps preparation separate from
execution and makes missing evidence visible.

The product contract is:

> Given a GitHub Actions incident definition and a GitHub organization or set of
> repositories, determine which historical workflow run attempts downloaded or
> executed an affected Action commit, reconstruct the historical workflow and
> dependency chain, identify credentials and resources potentially reachable by
> each affected job, and emit a verifiable incident-response evidence bundle.

The evidence model is the product. The graph is a derived view.

CIRewind is not a generic workflow scanner, Actions BOM replacement,
exploitation framework, secret-value collector, cloud compromise validator,
runner endpoint monitor, or hosted service. It supports GitHub.com only; GHES,
GitLab, Azure DevOps, and Jenkins are out of scope.

## Implemented commands

| Command | Purpose |
| --- | --- |
| `cirewind demo` | Generate and verify the deterministic synthetic case offline |
| `cirewind investigate` | Collect read-only GitHub.com evidence and generate a case |
| `cirewind archive` | Incrementally preserve compact execution facts before retention loss |
| `cirewind replay` | Apply a new incident pack to an archive without network access |
| `cirewind pack validate` | Strictly validate and canonicalize an incident pack offline |
| `cirewind verify` | Verify a case's SHA-256 manifest offline |
| `cirewind version` | Print version, source revision, and build time |

All important flags have command help. Default tests and the offline demo require
no GitHub credential or network access.

## Offline quickstart from source

After Go dependencies are available, this path uses only local synthetic data:

```sh
make build
./bin/cirewind pack validate incidents/synthetic/mutable-tag.yaml
make demo
./bin/cirewind verify demo-case
```

`make demo` creates a compact archive, replays the synthetic incident, emits a
complete case, verifies its manifest, and asserts canonical finding counts. It
refuses to overwrite an existing directory. Choose another new path with:

```sh
make demo DEMO_OUT=/new/path
```

The demo deliberately reports partial coverage. It proves deterministic offline
plumbing, not a real incident or universal GitHub.com completeness.

## Investigate GitHub.com

Networked commands resolve a token from `CIREWIND_GITHUB_TOKEN`, then
`GITHUB_TOKEN`, then `GH_TOKEN`. Tokens are read from the process environment;
they are never valid command arguments and must never be printed or persisted.

Use an explicit repository set when possible:

```sh
# After configuring a read-only token in the process environment:
./bin/cirewind investigate \
  --repo acme/service-a \
  --repo acme/service-b \
  --incident /path/to/reviewed-incident.yaml \
  --from 2026-03-19T17:00:00Z \
  --to 2026-03-20T06:00:00Z \
  --out cases/example
```

Organization collection uses the same evidence contract:

```sh
./bin/cirewind investigate \
  --org acme-corp \
  --incident /path/to/reviewed-incident.yaml \
  --from 2026-03-19T17:00:00Z \
  --to 2026-03-20T06:00:00Z \
  --out cases/example
```

The requested event window is half-open: `[from,to)`. The collector uses a
documented conservative parent-run discovery/watch interval for reruns and
delayed jobs. Organization enumeration and recursive time partitioning are
implemented, but dense-window saturation and the complete classic PAT,
fine-grained PAT, and GitHub App permission matrix are not live-qualified. Any
inaccessible or unsplittable scope must remain partial coverage.

## Archive and replay

Preserve compact facts incrementally, then apply an incident disclosed later:

```sh
./bin/cirewind archive \
  --repo acme/service-a \
  --since 24h \
  --store archive.db

./bin/cirewind replay \
  --archive archive.db \
  --incident /path/to/reviewed-incident.yaml \
  --out cases/new-incident

./bin/cirewind verify cases/new-incident
```

Archive polling uses per-repository checkpoints, a 15-minute overlap, and a
provisional 65-day parent watch. Explicit `--from` and `--to` are also supported.
Interrupted collection is recoverable; replay can read committed WAL facts, while
a clean close checkpoints the archive. Re-derivation does not rewrite archived
source facts.

Replay makes no network request. It cannot recover facts or raw bytes that an
older extractor did not retain. The measured relational envelope is 1,000
repositories, 100,000 runs, and 300,000 attempt/job/fact executions on the
documented reference host. Snapshot materialization rejects more than 1,000,000
facts or 256 MiB. Larger cases require partitioning or a later streaming design.

## Raw logs and privacy

Compact structured evidence is the default. Raw logs are opt-in because GitHub
masking does not guarantee that application output contains no secrets,
proprietary data, or personal information:

```sh
./bin/cirewind archive \
  --repo acme/service-a \
  --since 24h \
  --store archive.db \
  --raw-logs
```

A raw-enabled archive is the database plus its content-addressed
`archive.db.raw/` sidecar; preserve them together. `replay --raw-logs` copies
retained objects into the manifested case `raw/` directory. CIRewind never
retrieves, validates, hashes, or stores secret values.

Even compact cases can contain sensitive repository topology, actors, secret
names, permission scopes, runner labels, and environment names. Protect and
sanitize them before sharing. See [`PRIVACY.md`](PRIVACY.md).

## Evidence semantics

The mandatory invariants are:

```text
Action downloaded != Action executed
Repository possesses a secret != affected step could read that secret
id-token: write != cloud role assumed
Workflow ran during incident window != compromised SHA executed
Current tag points to a safe commit != historical runs were safe
No retained logs != no compromise
Deployment followed an affected step != attacker caused the deployment
Present-day workflow YAML != historical workflow definition
```

The only canonical finding states are:

- `CONFIRMED_EXECUTED`
- `CONFIRMED_DOWNLOADED`
- `CONFIRMED_CALLED_WORKFLOW`
- `DECLARED_AT_RUN_SHA`
- `RUN_IN_WINDOW_MUTABLE_REF`
- `POTENTIAL_TRANSITIVE`
- `CURRENT_REFERENCE_ONLY`
- `NO_MATCH_CONFIRMED`
- `UNKNOWN_EVIDENCE_GAP`
- `CONTRADICTORY_EVIDENCE`

The only canonical provenance identifiers are:

- `L4_CERTAIN`
- `L3_STRONG`
- `L2_PROBABLE`
- `L1_POSSIBLE`
- `L0_UNKNOWN`

Only an exact identity plus a separately correlated step lifecycle can support
`CONFIRMED_EXECUTED`. A completed preparation without a step start supports at
most `CONFIRMED_DOWNLOADED`. Missing evidence is never converted into a clean
bill of health.

Effective `GITHUB_TOKEN` permissions are runtime-observed where runner evidence
exists; a static fallback is labeled inferred. Named-secret relationships require
an exact reference, step mapping, reusable-workflow mapping/inheritance, or
environment-eligibility join. `id-token: write` is only
`OIDC_MINTING_CAPABILITY`; CIRewind performs no cloud trust-policy analysis.

## Qualification boundary

The controlled lab qualifies direct mutable Action execution, downloaded-only
skip behavior, attempt separation across tag movement and reruns, exact remote
Action/composite/reusable reconstruction, conservative named-secret and OIDC
relationships, runner classification, and missing-log gaps for its explicit
repository set.

The following remain experimental limitations:

- organization completeness at a saturated 1,000-result second;
- the complete live classic PAT, fine-grained PAT, and GitHub App matrix;
- live immutable Action package grammar and every runner version/localization;
- exact runtime bytes for unarchived local workspace Actions;
- broad secret, package, release, deployment, and runner inventory joins;
- cloud identity reachability, runner persistence, outbound data theft, or
  malicious causation; and
- replay above the documented fact/byte guards.

Unsupported syntax, missing definitions, denied routes, expired logs, and
ambiguous joins remain evidence gaps. See
[`ADR 0011`](docs/adr/0011-experimental-v0-1-qualification-envelope.md), the
sanitized [controlled-lab record](docs/validation/2026-08-22-controlled-lab-qualification.md),
and [`docs/IMPLEMENTATION_STATUS.md`](docs/IMPLEMENTATION_STATUS.md).

## Read-only permission profile

CIRewind probes capabilities independently and continues when optional access is
denied. It never requests write access.

| Purpose | Fine-grained PAT or GitHub App | Classic PAT | Core? |
| --- | --- | --- | --- |
| Private run, attempt, job, and log evidence | Repository `Metadata: read`, `Actions: read` | `repo` | Yes for private runtime evidence |
| Historical workflow and Action files | Repository `Contents: read` | `repo` | Yes for private reconstruction |
| Environment and relevant secret-name metadata | Repository `Environments: read`, `Secrets: read` | Endpoint-dependent `repo`/organization access | Optional |
| Current runner/settings context | Repository or organization administration read; self-hosted runner read where needed | Appropriate read administration access | Optional/current-state context |
| Artifacts and deployment context | Endpoint-specific Actions, Contents, or Deployments read | `repo`; optionally `read:packages` | Optional, non-causal |

The complete source-backed matrix and capability caveats are in
[`docs/GITHUB_DATA_SOURCES.md`](docs/GITHUB_DATA_SOURCES.md). A `404` under a
limited credential is not proof that a repository or object never existed.

## Security model

Workflow YAML, Action metadata, logs, ZIP archives, incident packs, names, API
errors, SQLite archives, and report fields are hostile input. CIRewind applies
bounded parsing, path and archive validation, output escaping, parameterized SQL,
strict CSP, terminal sanitization, and CSV formula neutralization. It never
executes, builds, imports, or installs downloaded Action code. Incident-pack
content cannot initiate network requests. There is no telemetry by default.

Report security issues privately through GitHub's **Security** tab and
**Report a vulnerability** workflow. See [`SECURITY.md`](SECURITY.md) and
[`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md).
