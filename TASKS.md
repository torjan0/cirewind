This is the ordered implementation and release-qualification checklist. It is subordinate to the normative [evidence model](docs/EVIDENCE_MODEL.md), [architecture](docs/ARCHITECTURE.md), [GitHub data-source matrix](docs/GITHUB_DATA_SOURCES.md), [incident-pack specification](docs/INCIDENT_PACK_SPEC.md), [threat model](docs/THREAT_MODEL.md), [test strategy](docs/TEST_STRATEGY.md), and [implementation plan](docs/PLAN.md). ## Status audit — 2026-08-22

The tree now contains a materially functional experimental v0.1 candidate; see
[`docs/IMPLEMENTATION_STATUS.md`](docs/IMPLEMENTATION_STATUS.md). The accepted
qualification envelope in
[`ADR 0011`](docs/adr/0011-experimental-v0-1-qualification-envelope.md) supersedes
the original assumption that every compatibility experiment must complete before
any public v0.1. It does not narrow the evidence model, hostile-input rules, or
candidate-release integrity gates.

The controlled GitHub.com explicit-repository lab completed the central harmless
A→B→A protocol. It retained exact affected B execution, affected B download with
no step start, and restored A on a later attempt without merging attempts or
consulting the current tag. Full/failed/single-job reruns remained distinct;
GitHub-recorded reusable-workflow tag objects remained separate from peeled
commits; missing logs produced `UNKNOWN_EVIDENCE_GAP`; credential, OIDC,
environment, runner, and downstream language remained conservative. The final
raw-disabled candidate archive/replay, case-manifest, SQLite, and offline browser
audits passed and are recorded without private identifiers in the
[`controlled-lab qualification`](docs/validation/2026-08-22-controlled-lab-qualification.md).

Implemented and broadly offline-tested surfaces include all CLI commands, the
canonical evidence/domain model, strict incident packs, SQLite archive/case
stores, interruption recovery, hostile ZIP/log parsing, non-executing historical
resolution, matching, exposure derivation, graph/report generation, raw opt-in,
manifest verification, GitHub transport/collector mocks, and deterministic A–Q
acceptance fixtures. Public and controlled read-only observations exercise the
current consolidated runner-log layout, exact traditional Action identities,
separate attempts, reusable metadata, historical definitions, runner context,
and retention loss.

Fuzz campaigns covered 11 parser/domain targets; an extended three-minute ZIP
campaign passed 4.3 million executions. Synthetic streaming parses at 5 GiB and
50 GiB stayed near-linear with stable RSS and no false lifecycle observation.
The measured relational envelope is 1,000 repositories, 100,000 runs, and
300,000 executions. A 3,000,000-execution run exceeded two hours and remains
unsupported. Replay separately rejects more than 1,000,000 facts or 256 MiB of
materialized compact data. These results do not complete the intentionally broad
`SEC-002`, `PERF-001`, or `PERF-002` contracts, so those boxes remain open.

Checkboxes below are aggregate planning contracts. A box is checked only when
its entire original `Done when` clause—not a narrowed v0.1 support claim—is
objectively satisfied. Consequently, many boxes remain open even though their
implemented subset is sufficient for the experimental release decision. The
status documents and public-release checklist are the authoritative record of
what v0.1 actually supports.

Remaining release blockers are candidate-scoped: full exact-revision
test/vet/race/security/release checks, staged/private-data review, clean hosted
CI, repository security settings, protected draft and publish environments,
annotated tag, artifact/attestation inspection, and public publication.
Organization saturation, full token-type qualification, live
immutable-package grammar, all runner versions, broad resource inventories,
local workspace proof, and data above the measured scale envelope are explicit
nonblocking experimental limitations only because output remains partial.

No phase may execute, import, build, source, or check out fetched Action code;
fetched workflows, metadata, logs, archives, packs, names, and API strings are
hostile data. Task IDs remain useful dependency/review references even when their
broader research completion is deferred.

- [ ] **P0-001 — Establish the controlled lab and handling rules.** Create two private synthetic fixture repositories and an organization test owner; use harmless Actions, fake secret names/values, an isolated self-hosted runner, and no exfiltration or destructive payloads. Record repository IDs, permissions, fixture commit identities, token kind (never token material), GitHub.com date, and sanitization procedure. **Done when:** an independent reviewer can reproduce the lab from a checked-in recipe, the fixture inventory contains no credential or customer data, and every captured response/log has a sanitized provenance record. *(Tests: `SEC-LAB-001`; dependencies: `P0-000`.)*

- [ ] **P0-002 — Verify the GitHub.com endpoint and authorization matrix.** Probe the required REST API with `X-GitHub-Api-Version: 2026-03-10`, the current GraphQL schema, and the optional organization audit log using representative classic PAT, fine-grained PAT, and GitHub App installation-token access described in [GITHUB_DATA_SOURCES.md](docs/GITHUB_DATA_SOURCES.md).
