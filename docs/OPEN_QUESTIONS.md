# CIRewind decision and open-question register

This register separates settled product contracts from questions that still require evidence. It is not a backlog: implementation work belongs in [`TASKS.md`](../TASKS.md), feasibility experiments in the [fixed spike](PLAN.md#fixed-two-week-feasibility-spike), and endpoint details in the [GitHub data-source matrix](GITHUB_DATA_SOURCES.md). All external primary sources linked here were retrieved on **2026-08-20**.

> **Status update (2026-08-22):** the controlled explicit-repository lab
> satisfied the central A→B→A, baseline read-credential, harmless self-hosted,
> and compact evidence-custody prerequisites. The full organization/token/runner
> compatibility matrix and pre-aged 65-day boundary remain open. ADR 0011 makes
> those explicit experimental-v0.1 limits instead of silently treating them as
> successful coverage. Rows below retain their stable planning IDs; consult the
> [implementation status](IMPLEMENTATION_STATUS.md) for current qualification.

Status labels are normative in this document:

- **Fact** — directly supported by a cited primary source or a reproducible, pinned upstream source revision.
- **Decision** — a settled CIRewind product or architecture rule. It is not presented as a GitHub fact.
- **Inference** — a conservative conclusion drawn from facts; its premises and limit are stated.
- **Assumption** — a proposition that must be tested against live GitHub.com before it is treated as implementation truth.
- **Unknown** — evidence is presently insufficient. An unknown is never silently converted into an assumption or a negative conclusion.

Questions are assigned stable IDs so spike records and later ADRs can refer to them without depending on headings or prose.

The spike must record the account/repository, request shape, API version, response status and relevant headers, runner version when known, source hashes, collection time, and a sanitized fixture. A failure follows the stated conservative outcome; it is never papered over with current YAML or a current tag lookup.

provides limited observations relevant to AV-02, AV-04, AV-05, AV-09, and AV-11:
a low-density created-time query, two independently addressable attempts,
retained and unavailable attempt/job logs, two consolidated whole-job archive
layouts, and one exact `referenced_workflows` SHA. A later bounded parser pass

## Later-version questions

These questions are intentionally outside v0.1. They must not expand the builder's authority or weaken v0.1 evidence semantics.

| ID | Status | Later question | Current boundary |
| --- | --- | --- | --- |
| LV-01 | **Decision deferred** | Which GitHub Enterprise Server versions and capability probes could be supported? | v0.1 is GitHub.com only. Do not infer parity for REST versions, `$/`, immutable packages, audit fields, or log grammars. See [GHES exclusion](GITHUB_DATA_SOURCES.md#18-github-enterprise-server-exclusion). |
| LV-02 | **Decision deferred** | Should static AWS, Azure, GCP, Vault, or infrastructure-as-code trust adapters establish `CLOUD_IDENTITY_REACHABLE`? | v0.1 reports only `OIDC_MINTING_CAPABILITY` from `id-token: write`. A future adapter must parse a compatible relying-party trust policy and still cannot claim a token exchange or role assumption without direct evidence. |
| LV-03 | **Decision deferred** | How should community packs be signed, indexed, revoked, and distributed? | v0.1 validates a local declarative file and records byte/canonical hashes plus repository provenance; a hash is not publisher authentication. Signing must not change logical indicator/finding identity. |
| LV-04 | **Decision deferred** | Can a privacy-preserving future archive improve arbitrary literal/IOC replay without storing raw logs? | v0.1 makes no such promise. Probabilistic indexes cannot support verifiable positive evidence, and an unarchived literal remains `UNKNOWN_EVIDENCE_GAP`. Any future design needs explicit false-positive/false-negative, disclosure, and chain-of-custody analysis. |
| LV-05 | **Decision deferred** | Should CIRewind parse cloud audit, network, endpoint, or runner telemetry to prove token exchange, exfiltration, persistence, or causation? | Such telemetry is outside GitHub-only v0.1. It must enter through typed evidence adapters and cannot retroactively strengthen a GitHub observation without a cited join. |
| LV-06 | **Decision deferred** | Which internal tool/package downloads by arbitrary Actions can be reconstructed? | v0.1 parses historical metadata and retained literal/immutable records but never executes Action code. General package-malware analysis and dynamic observation remain non-goals. |
| LV-07 | **Decision deferred** | Should another source-of-truth database or graph database be introduced for very large/multi-case deployments? | SQLite plus append-only JSONL is the v0.1 source of truth; graphs are deterministic projections. Reconsider only with measured limits that SQLite cannot meet, not for visualization convenience. |
| LV-08 | **Decision deferred** | Which additional forges/CI systems should be supported? | GitLab, Azure DevOps, Jenkins, and generic CI abstractions are explicit non-goals. A future adapter must preserve attempt, evidence, and credential distinctions rather than force GitHub semantics onto another system. |
| LV-09 | **Decision deferred** | Should CIRewind offer hosted collaboration, enterprise identity, or a control plane? | v0.1 is a local, read-only CLI with no SaaS account or telemetry by default. Any hosted design requires a separate privacy, tenancy, key-management, retention, and threat model. |
| LV-10 | **Decision deferred** | Can archive collection be event-driven through GitHub Apps/webhooks while retaining portable PAT-based completeness? | No mandatory GitHub App in v0.1. Future notification paths may reduce polling latency but cannot silently redefine the repository universe or eliminate periodic reconciliation. |
| LV-11 | **Decision deferred** | How should newer runner grammars and retired historical grammars be distributed and trusted over time? | v0.1 parsers are versioned and fixtures are pinned. Future grammar bundles must be declarative/non-executable, signed or release-bound, fuzzed, and incapable of initiating network requests. |
| LV-12 | **Decision deferred** | Can historical repository settings, environment rules, runners, and secret metadata be obtained from independent archives? | v0.1 treats live settings as collection-time context unless GitHub provides contemporaneous evidence. A future adapter must preserve event and collection times and may not back-project current state. |
